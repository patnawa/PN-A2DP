# Release readiness: free GitHub or paid

Audit date: **12 October 2026 (Asia/Bangkok)**. This is an engineering and published-cost assessment, not a legal clearance or vendor quotation. Prices retain the supplier's currency; tax, exchange rates and local professional fees are not estimated.

**Recommendation:** release the Windows-mode application first if avoiding paid enrollment is the priority. Keep the custom driver as an explicitly experimental developer build until production signing, broader hardware testing and applicable licensing/qualification are resolved. Giving it away removes billing work; it does not change Windows kernel signing policy or automatically waive distribution obligations.

## What is established locally

The audit baseline was application 0.1.0.28 and custom driver 0.1.0.17. The subsequent [reliability update](16-reliability-improvements.md) installed application 0.1.0.30 and driver 0.1.0.18 and records the newer checks. Sony SBC playback, volume/mute, reconnects and installer recovery have machine-test evidence. AAC, aptX and LDAC encoder tests are not proof of receiver interoperability. Physical power-cycle detection, sleep/wake, other adapters/receivers, Driver Verifier and HLK coverage remain incomplete. See the [test record](06-testing-plan.md), [Windows-mode limits](13-windows-mode.md) and [codec license audit](05-codec-licensing.md).

The repository's [MIT license](../LICENSE) permits free distribution and sale of MIT-covered code with its notice retained. It does not relicense bundled dependencies or make previously distributed MIT code exclusive. No account enrollment, purchase, repository visibility change or public release is performed by this audit.

## Fixes prepared in application build 0.1.0.29

- Full and portable codec packages now include the complete upstream licenses/notices and offline corresponding-source archives, including nested LDAC sources, PN adapters, headers and rebuild instructions. Hash manifests connect the source archives and notices to the actual DLLs. The build refuses missing or stale redistribution artifacts. Windows-mode packages exclude these encoders.
- Removed blanket patent-expiry/royalty assumptions from the codec documentation and corrected the installer's AAC description to AAC-LC.
- Removed `%ProgramData%\PN-A2DP\plugins` from codec-host discovery. The installed service runs as LocalSystem; this machine's ProgramData root allows ordinary users to create children. A benign regression fixture reproduced a plugin load from that location before the change and confirmed it is ignored afterward. Installed-directory plugins and built-in SBC still load. The fixture uses `--list-plugins`, which never opens an audio device or installs a service.
- Rejected truncated plugin-directory paths and removed the old unsafe plugin-folder suggestion from the installer and API header.

**Follow-up in application 0.1.0.30:** the installer, shared service-registration helper, host `--install` and service startup now enforce a protected-path policy covering ownership, DACLs, ancestor replacement, reparse points and hard links. Unsafe paths fail before privileged installation writes or service registration. The default Program Files location is the intended deployment. Descriptor/path regression tests and the installed-tree check accompany this fix; adversarial standard-user tampering on a clean machine, a whole-kernel/IOCTL security review and release-history/secret review are still outstanding. See the [follow-up implementation and validation record](16-reliability-improvements.md).

Validation on this machine: **20 software verification groups passed**, including 25,899 core checks, codec parameter tests, independent SBC/AAC/aptX decoding, real plugin discovery, payload matching and 14 negative redistribution cases. **Seven Windows-mode checks and seven installer signing-policy checks passed.** Each AAC, aptX and LDAC archive rebuilt into a DLL outside a Git checkout with the documented `-SkipSourceBundle` command. LDAC independent decoding and physical optional-codec receiver tests remain unverified.

Historical audit result: build 0.1.0.29 installers and portable packages were prepared under `out/Release/dist` and `dist-windows`. Logs are under `out/commercial-audit` and `out/verification/20261012-181626`. **That audit did not install its build**; the running app/host were then 0.1.0.28 with kernel 0.1.0.17. The later 0.1.0.30 update installed the host discovery and protected-path fixes; its evidence is recorded separately above. No reboot, boot-policy change, clean-machine retail installation or HLK run is claimed by either update.

## Three practical release routes

| Route | What users receive | Lowest justified cost statement | Release decision |
| --- | --- | --- | --- |
| Free Windows-mode app on GitHub | Diagnostics and controls using the existing Windows audio driver; no PN kernel or bundled codec encoders | **$0 hosting and no PN kernel-signing purchase.** Unsigned app warnings remain; conditional free app signing may be available | Best low-cost first route after packaging, clean-machine and public-release checks |
| Free custom driver, initially SBC only | PN kernel codec control, adaptation and recovery | **No defensible $0 normal-install route established.** EV/signing prerequisites, applicable Bluetooth qualification and testing remain | Experimental developer distribution only for now; not advertised as a normal-install stable release |
| Paid custom driver, optionally full codecs | Same kernel product plus payment/support obligations | Same driver costs, plus applicable codec rights and transaction fees; **all-in minimum unknown** | Do not take payment for a general release until the gates below are satisfied |

An SBC-only package reduces the AAC/aptX/LDAC dependency and clearance scope; it does not itself waive Bluetooth qualification or establish patent clearance. A full-codec free release needs the same codec review as a paid one. Windows mode cannot promise PN bitrate selection or custom codec support through APIs that Windows does not expose.

## Microsoft signing and the Thailand enrollment issue

1. Hardware enrollment requires an EV certificate, an Entra global-administrator account, a legal contact, company information and approval. The current instructions allow manual company details when there is no D-U-N-S match. They do **not** give a clear Thailand unregistered-individual acceptance rule. The owner's prior TIN rejection therefore remains unresolved. [Microsoft enrollment](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/hardware-program-register)
2. SSL.com advertises sole-proprietor EV without a separate business entity. Its validation guide additionally requires identity documentation, a notarized/qualified professional verification form and an acceptable independent business listing. Certificate issuance and Microsoft account approval are separate decisions. **Written eligibility confirmation from both should precede payment.** [Validation guide](https://www.ssl.com/guide/sole-proprietor-ev-application/)
3. Thailand's Revenue Department says an individual who uses a civil-registration personal identification number need not apply for a separate TIN. This does not prove that Microsoft's business field accepts it or that business registration is unnecessary. Ask Microsoft which legal-account category and evidence it accepts; do not enter a made-up company or tax number. Do not put identity documents or tax numbers in this repository. [Revenue Department](https://www.rd.go.th/english/21987.html)
4. Microsoft currently describes attestation as **testing-only** and recommends HLK testing for production. It cannot publish attestation packages to retail Windows Update. Plan a WHCP submission with the required HLK results; determine the precise audio/Bluetooth driver category with Microsoft. [Signing options](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/driver-signing-offerings)
5. A paid EV signature on our own `.sys` alone is not the modern retail kernel approval path. Microsoft's current driver policy directs publishers through WHCP; legacy cross-signing exceptions are not a new-product strategy. [Windows Driver Policy](https://support.microsoft.com/en-us/windows/hardware/drivers/the-windows-driver-policy)
6. Release qualification must include Secure Boot and Memory Integrity enabled, plus code-integrity/HLK tests. A successful Test Mode installation with those protections disabled cannot establish that compatibility. Do this on a recovery-ready test machine. [Microsoft HVCI guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/driversecurity/implement-hvci-compatible-code)

For a free Windows-mode app, SignPath may reduce Authenticode costs, but it is discretionary: its terms require OSI-licensed components, active maintenance, an existing release, a documented signing/privacy policy, MFA and controlled release approval. The full FDK-containing bundle must not be assumed eligible. We have not applied or received approval. A SignPath app signature does not establish a Microsoft-signed PN kernel. [SignPath conditions](https://signpath.org/terms.html)

Microsoft's app-signing guidance also offers Store-managed MSIX signing, but that requires Store enrollment and different packaging. Azure Artifact Signing's published individual eligibility is US/Canada, so it is not a confirmed shortcut for this Thailand individual. Neither route is a replacement for custom kernel submission. [App signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)

## Bluetooth and codec clearance

Bluetooth SIG's qualification page covers products that are **sold or distributed**, so a zero price is not a stated exemption. Its QPRD requires a qualifying design to contain at least one complete Bluetooth layer. PN's custom A2DP/AVDTP implementation warrants a specific assessment; a Windows-mode control application that merely uses existing Windows functions has a different scope. **This audit does not decide that either package owes a qualification fee.** Get a written determination with the architecture attached. [Qualification overview](https://www.bluetooth.com/develop-with-bluetooth/qualify/), [QPRD v5](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/QPRD/out/en/index-en.html)

Do not assume the radio manufacturer's or Microsoft's qualification transfers to our new implementation, or that removing a logo alone resolves all obligations. SIG's product-scenario guidance distinguishes products represented as one's own from unchanged resale and invites product-specific support requests. Use its answer to establish required design/layer evidence, membership eligibility, test plan and fees. [Product scenarios](https://qualification.support.bluetooth.com/hc/en-us/articles/28365711158285-Trademark-Licenses-Qualification-Requirements-by-Product-Scenario)

Codec copyright licenses, patent rights and branding/certification are different checks:

- **FDK AAC:** the notice grants source/binary redistribution subject to its conditions, explicitly excludes patent licenses and requires complete source availability to binary recipients. Paying nothing for the software does not remove those conditions. Package the exact source and notices; separately establish whether patent clearance is required in intended territories. [FDK notice](https://github.com/mstorsjo/fdk-aac/blob/master/NOTICE)
- **AAC pricing:** request Via LA's PC-software category and written treatment of free/open-source AAC-LC distribution, the exact encoder implementation and intended markets. Its generic table is not sufficient to calculate our liability. [Via LA](https://www.via-la.com/licensing-programs/aac/)
- **aptX:** review the actual libfreeaptx license and modified-source/build obligations independently of any Qualcomm patent, certification or trademark position. This audit found no PN-specific published royalty; it makes no patent-expiry or royalty-free assertion. Qualcomm describes aptX as its proprietary technology family. [Qualcomm aptX](https://www.qualcomm.com/audio/technologies/aptx)
- **LDAC:** preserve Apache license and upstream notices. Sony distinguishes its AOSP smartphone source implementation from licensed sink software and offers a licensing inquiry process. Those statements are not an explicit clearance for this Windows sender. Ask specifically about the Windows source encoder, free and paid builds, and branding/certification. [Sony developer information](https://www.sony.co.jp/en/Products/LDAC/), [AOSP information](https://www.sony.co.jp/en/Products/LDAC/aosp/)

The reduced-risk scope is to omit optional codec binaries until their release obligations are established. This is a packaging choice, not a declaration that SBC has no possible IP obligations. The [codec audit](05-codec-licensing.md) records implementation-level requirements.

## What the owner must do before public release or sale

1. **Choose the release:** Windows mode, clearly labeled experimental source/developer build, or production custom driver. For free GitHub, choose public-source visibility explicitly; inspect history, backups, credentials, local diagnostics and third-party material before changing it. Publish installer hashes, license texts and matching source bundles with the exact release tag.
2. **Get eligibility answers before spending.** Send the questions below yourself. Enrollment, identity verification, legal agreements and rights-holder decisions cannot be completed by a code change.
3. **Approve a limited compatibility promise.** Start with the tested OS/architecture/adapters/receivers and codecs. Complete clean install/upgrade/uninstall/rollback, long playback, sleep/wake, radio and receiver reconnects, service failure recovery, standard-user controls and security-setting tests. Do not advertise all codecs or universal adapter support based on encoder unit tests.
4. **For the custom driver, complete the signing/qualification path.** Obtain the appropriate account/certificate only after acceptance is confirmed, run the required HLK/verification work, receive the returned Microsoft-signed package and verify it on a clean retail Windows installation without Test Mode.
5. **Close distribution obligations.** Review the final binary bill of materials, exact licenses/notices/source, LGPL replacement/relinking obligations, any applicable patents and permitted codec/logo claims. Source availability alone does not settle every right.
6. **Prepare support and privacy information.** Publish known limitations, removal/recovery instructions, a security-report contact and what diagnostic exports contain. Review exports before attaching them to public issues. A free release still needs accurate expectations and a workable recovery route.
7. **Only if selling:** establish the seller identity/bank/tax status, provider approval, clear price, support/update terms and refund policy before accepting money. A merchant of record's transaction-tax handling is not proof that the owner's Thai income/business obligations disappear. Obtain advice for the actual business arrangement.

## Decision today

**Go:** prepare the narrowly described Windows-mode release; use free GitHub hosting and consider conditional free app signing. **No-go for a general custom-driver launch today, free or paid:** production signing, qualification applicability/fees, optional codec clearance and wider hardware/security testing remain open. The custom service-path fix above still needs adversarial deployment testing. A free custom-driver binary release has the same technical and distribution gates; labeling it free does not resolve them. No complete minimum custom-driver launch budget can be stated until the written answers arrive.
